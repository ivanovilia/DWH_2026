# ДЗ 2.3 

## 1. Окружение и исходные данные

Решение выполнено в Docker с Apache Airflow 2.10.5, Apache Spark 3.5.4 (PySpark), Hadoop 3.3.4, RustFS 1.0.4 и PostgreSQL 16.6.  Часовой пояс расчётов — **UTC**.

Взят основной набор `demo` из комплекта: **6000 событий 100 пользователей**, `seed=42`, шесть CSV-файлов. Источники размещаются в S3-совместимом хранилище RustFS:

- события: `s3://hw23/raw/demo/events/`;
- справочник рассылок: `s3://hw23/raw/demo/campaigns.csv`.

Результаты сохраняются в Parquet с разделением по датам:

- `s3://hw23/results/demo/user_scd2/snapshot_date=YYYY-MM-DD/`;
- `s3://hw23/results/demo/campaign_recipients/calculation_date=YYYY-MM-DD/`.

Подключение Spark к S3, чтение исходных данных и запись проверены: `OK: Spark 3.5.4, Hadoop 3.3.4, S3A write/read, input data` (`reports/check_environment.txt`).

## 2. DAG и расписание

Создан DAG `hw23_daily_scd2_campaigns` с последовательностью задач:

`build_user_scd2 → build_campaign_recipients`.

Первая задача строит историю изменений профилей пользователей на конец обрабатываемых суток. Вторая берёт **снимок SCD2 той же даты** и определяет получателей кампаний. Между задачами передаются параметры запуска, а не сами таблицы.

Расписание — **ежедневно в 00:00 UTC**, с суточными интервалами `[data_interval_start, data_interval_end)`. Настройки: `catchup=True`, `max_active_runs=1`, одна повторная попытка при ошибке. Планировщик Airflow самостоятельно выполнил три исторических запуска типа `scheduled`:

- `scheduled__2026-01-23T00:00:00+00:00` — обработка 23 января, интервал до 24 января;
- `scheduled__2026-01-24T00:00:00+00:00` — обработка 24 января, интервал до 25 января;
- `scheduled__2026-01-25T00:00:00+00:00` — обработка 25 января, интервал до 26 января.

Все шесть задач завершились успешно. Подтверждения: `reports/airflow_three_scheduled_runs.png` и `reports/airflow_tasks_graph.png`.

## 3. Результаты и правильность расчётов

| Дата обработки | Версий SCD2 | Пользователей | Получателей рассылок |
| --- | ---: | ---: | ---: |
| 2026-01-23 | 961 | 100 | 53 |
| 2026-01-24 | 995 | 100 | 25 |
| 2026-01-25 | 1036 | 100 | 22 |

SCD2 - Для каждого снимка проверены уникальность `(user_id, valid_from)`, одна актуальная версия на пользователя, непрерывность интервалов `[valid_from, valid_to)`, отсутствие неверных и лишних версий, а также отсутствие будущих событий. Нарушений нет.

Получатели рассылок - Отбор выполняется по домену электронной почты, действовавшему на момент `send_at`, с учётом исторического интервала версии. Проверены отсутствие дублей `(campaign_id, user_id)`, совпадение домена и даты, а также сравнение сохранённого результата с повторно рассчитанным JOIN посредством `exceptAll` в обе стороны. Различий нет: `missing=0, extra=0`.

По кампаниям получено: 23 января — `campaign_id=11` (10 получателей), `16` (23) и `23` (20); 24 января - `campaign_id=21` (25); 25 января - `campaign_id=19` (22).

На отдельном наборе `fixtures` проверены граничные случаи, включая смену профиля точно в момент отправки, повтор события без изменений, возврат к прежнему логину и пустой результат. Проверка завершилась успешно(`reports/check_fixtures.txt`).

## 4. Метаполя запусков

В обеих таблицах заполнены обязательные метаполя:

`_dag_id`, `_run_id`, `_task_id`, `_data_interval_start`, `_data_interval_end`, `_loaded_at`.

Проверки показали отсутствие `NULL` в метаполях. Для одного дня у двух задач одинаковые `_dag_id`, `_run_id` и границы интервала; `_task_id` соответствует записавшей задаче. В пределах одной записи результата время `_loaded_at` фиксируется при выполнении расчёта.

 Сводки приведены в `reports/check_before.txt` и `reports/check_after.txt`.

## 5. Способ соединения таблиц

В качестве способа соединения выбран Broadcast Hash Join, поскольку справочник кампаний небольшой и может быть передан каждому рабочему процессу Spark без перераспределения большой таблицы пользователей.

Физический план подтвердил использование операторов `BroadcastHashJoin Inner BuildRight` и `BroadcastExchange` (`reports\join_physical_plan.png`).

Также подтверждено, что при соединении учитываются исторические версии профилей.

## 6. Проверка повторного выполнения

После трёх успешных запусков сохранены исходные результаты  `validate_results.py --phase before`. Затем обе задачи первого запуска, за 23 января повторно выполнены через Airflow Clear. Для этой даты время `_loaded_at` изменилось, но исходный `_run_id` сохранился.

Команда `validate_results.py --phase after` подтвердила:

- за 23 января содержимое обеих таблиц совпало с исходным по всем бизнес-полям и дате;
- за 24 и 25 января данные остались неизменными;
- дубликатов, нарушений интервалов и неверных получателей не появилось.

Итог: (`reports/check_after.txt`). Это подтверждает повторяемость вычислений и независимое обновление партиций по датам.
