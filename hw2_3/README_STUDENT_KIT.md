# ДЗ 2.3: материалы для студентов

Условие и критерии оценки: [hw_2_3.docx](hw_2_3.docx) или [ASSIGNMENT.md](ASSIGNMENT.md).

В комплекте подготовлены окружение и исходные данные. Учебный DAG, запуск расчётов из задач, передача интервалов, запись метаполей и проверки результата — ваша работа. Используйте свои решения SCD2 и JOIN из ДЗ 2.1 и 2.2.

## Содержимое

| Путь | Назначение |
| --- | --- |
| `docker-compose.yaml`, `docker/`, `.env.example` | Airflow, PostgreSQL, Spark и S3-совместимое хранилище RustFS |
| `data/demo/` | Основной набор: 6 000 событий профилей и рассылки из ДЗ 2.2 |
| `data/fixtures/` | Небольшие входные данные для проверки граничных случаев |
| `scripts/generate_event_log.py` | Генератор исходных событий |
| `scripts/upload_data.py` | Загрузка исходных CSV в S3 |
| `scripts/check_environment.py` | Отдельная проверка подключения Spark к S3 |
| `dags/` | Пустая папка для вашего DAG |
| `jobs/` | Пустая папка для вашего кода расчётов |

Ожидаемых выходных таблиц, готового учебного DAG и функций расчёта в комплекте нет. `.gitkeep` лишь сохраняет пустые папки в архиве.

## 1. Поднять стенд

Нужен Docker Engine / Docker Desktop с Compose v2. Рекомендуется выделить Docker 6–8 ГБ RAM и иметь около 10 ГБ свободного места. Первая сборка скачивает образы и зависимости из Docker Hub, Debian, PyPI и Maven Central.

Откройте терминал в этой папке:

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps -a
```

Дождитесь `healthy` у PostgreSQL, RustFS, webserver и scheduler. Сервисы `volume-init`, `airflow-init`, `s3-init` должны завершиться с кодом `0` — это одноразовые шаги подготовки. Исходные данные `demo` и `fixtures` загружаются автоматически.

| Сервис | Адрес на компьютере | Учебные данные входа |
| --- | --- | --- |
| Airflow | http://localhost:8080 | `student` / `student` |
| RustFS Console | http://localhost:9001 | `hw23student` / `hw23student-secret` |
| S3 API | http://localhost:9000 | Те же ключи, что для RustFS |

Порты и пароли задаются в `.env`. Порты стенда доступны только на `127.0.0.1`. Если порт занят, измените его в `.env` и повторите `docker compose up -d`.

Если сервис не запустился:

```bash
docker compose logs --tail=100 airflow-init s3-init airflow-scheduler
```

## 2. Проверить подключение

При уже работающем стенде выполните:

```bash
docker compose run --rm --no-deps tools python /opt/airflow/scripts/check_environment.py
```

Скрипт записывает три технические строки через Spark в S3, читает их обратно и удаляет только свои временные объекты. Ожидаемое сообщение — `OK: Spark ..., Hadoop ..., S3A write/read, input data`. Это проверка инфраструктуры, она не рассчитывает учебные таблицы и не является DAG.

Флаг `--no-deps` исключает повторный запуск сервисов инициализации и загрузки данных при этой проверке.

В образе установлены Airflow 2.10.5, PySpark 3.5.4, Hadoop 3.3.4, Java 17 и библиотеки S3A; хранилище — RustFS 1.0.4. Spark работает в режиме `local[2]` внутри контейнера. Отдельный кластер Spark, HDFS и Hive для задания не требуются.

Параметры подключения доступны внутри контейнеров:

| Переменная | Значение по умолчанию |
| --- | --- |
| `S3_ENDPOINT` | `http://rustfs:9000` |
| `S3_BUCKET` | `hw23` |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Учебные ключи из `.env` |
| `AWS_DEFAULT_REGION` | `us-east-1` |
| `SPARK_MASTER` | `local[2]` |

Для Spark используйте `s3a://`. Настройки подключения Spark можно посмотреть в проверочном скрипте. В своём расчёте явно установите часовой пояс UTC. Внутри контейнера `localhost:9000` не является адресом сервиса RustFS.

## 3. Выполнить задание

1. Напишите свой DAG в `dags/`. При первом запуске стенда список учебных DAG пуст — это ожидаемо.
2. Разместите код расчётов в `jobs/`. Эти папки доступны контейнерам как `/opt/airflow/dags` и `/opt/airflow/jobs`.
3. Организуйте вызов расчётов из двух зависимых задач. Определите, как передавать в них контекст запуска Airflow и период обработки.
4. Адаптируйте SCD2 и исторический JOIN из предыдущих работ, добавьте метаполя и сохранение результатов по датам.
5. Настройте расписание, повторные попытки и ограничение одновременных запусков согласно условию.
6. Выполните проверки и подготовьте материалы для сдачи из раздела 6 условия.

После изменения Python-файлов пересобирать образ не нужно: они смонтированы в контейнеры. Ошибки импорта DAG можно проверить командой:

```bash
docker compose exec airflow-scheduler airflow dags list-import-errors
```

Новый DAG по умолчанию выключен. Включите его после подготовки кода и расписания. Для сдачи нужны три запуска, созданные scheduler, с интервалами за 23, 24 и 25 января 2026 года. Ограничьте диапазон расписания этими сутками. В Airflow 2.10.5 с `CronDataIntervalTimetable` граница `end_date` включительно ограничивает начало последнего интервала.

Перед повтором первого запуска сохраните копии результатов за все три даты. Затем используйте Clear для обеих задач только этого запуска. Сравните бизнес-результат до и после; у следующих дат должны сохраниться также метаполя. Очистка состояния задачи в Airflow не удаляет её данные в S3.

## 4. Исходные данные

Основные входы:

```text
s3://hw23/raw/demo/events/*.csv
s3://hw23/raw/demo/campaigns.csv
```

Имена, схемы выходных таблиц и правила обработки описаны в условии. Результаты удобно размещать под `s3://hw23/results/demo/`; конкретные пути укажите в отчёте. В исходные каталоги `raw/` результаты не записывайте.

Набор `fixtures` находится в `s3://hw23/raw/fixtures/` и содержит 14 событий и 16 рассылок. Используйте его для самостоятельной проверки исторических границ, повторов, смены атрибутов и пустого результата. Проверки и ожидаемые результаты сформулируйте сами. Даты этого набора не нужно добавлять в расписание основного DAG.

Повторно генерировать данные для основной сдачи не требуется. Подробности и команда воспроизведения — в [data/README.md](data/README.md).

## 5. Большой набор из ДЗ 2.2 — необязательно

Для основной сдачи достаточно `demo`. Если используете большой набор из предыдущей работы, положите его CSV в `data/full/events/`, а `campaigns.csv` — в `data/full/`. Для новой генерации локальным Python 3.9+:

```bash
python3 scripts/generate_event_log.py \
  --rows 5000000 --users 100000 --change-probability 0.20 \
  --seed 42 --start-time 2026-01-01T00:00:00Z --max-step-seconds 1 \
  --rows-per-file 100000 --output-dir data/full/events
cp data/demo/campaigns.csv data/full/campaigns.csv
docker compose run --rm --no-deps tools python /opt/airflow/scripts/upload_data.py --dataset full
```

Источник появится в `s3://hw23/raw/full/`. Настройте на него свой расчёт и укажите выбранный набор в отчёте. Производительность на миллионах строк в этой работе не оценивается.

Не меняйте исходные данные между проверочными запусками. Загрузчик перезаписывает одноимённые объекты и останавливается при обнаружении лишних CSV от другого набора; автоматически их не удаляет.

## 6. Остановка

```bash
docker compose stop       # остановить, сохранив данные
docker compose up -d      # запустить снова
docker compose down       # удалить контейнеры, сохранив именованные тома
```

Команда `docker compose down -v` удалит также данные RustFS, историю Airflow и логи. Она нужна только для намеренного полного сброса.

Документация: [Airflow 2.10.5](https://airflow.apache.org/docs/apache-airflow/2.10.5/), [интервалы DAG](https://airflow.apache.org/docs/apache-airflow/2.10.5/core-concepts/dag-run.html), [Spark 3.5.4](https://spark.apache.org/docs/3.5.4/).
