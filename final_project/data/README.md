# Данные для итогового проекта

Готовые входные файлы уже приложены. Для первого запуска генерировать их заново не нужно.

| Набор | Содержимое |
|---|---|
| `fixture/` | 3 пользователя, 26 уникальных событий и 8 уникальных сообщений об изменении профиля. С повторами — 28 и 9 сообщений соответственно. Небольшой набор для ручной проверки. |
| `demo/` | 100 пользователей, 6 000 уникальных событий за три дня, изменения профилей, повторы и поздние доставки. Подходит для первого сквозного запуска. |
| `catalogue.jsonl` | Общий исходный каталог из 200 объектов для генератора. Его копия находится внутри каждого набора. |

Каждый набор содержит `catalogue.jsonl`, `events.jsonl`, `profile_changes.jsonl` и `manifest.json`. JSONL — один JSON-объект на строку. Manifest описывает параметры и объём входа; в Kafka его отправлять не нужно.

## Что переиспользовано

Каталог получен из `data4hw2_2/task2/catalogue.json`: взяты первые 200 объектов с положительной длительностью при сортировке по числовому ID. Идентификаторы сохранены, `type` переименован в `category`. Для проекта исходная длительность трактуется как минуты и переводится в секунды. Категории здесь — типы контента (`movie`, `series`, `multipart_movie`), а не жанры.

Просмотры, поиск и профили синтетические и согласованы по идентификаторам. Генератор развивает сценарий изменения профилей из ДЗ 2.1/2.3, но использует страну и тариф. Старые транзакции не перенесены: в них нет времени события, необходимого для исторического JOIN.

## Контракт данных

Все даты — UTC в формате `2026-01-01T00:00:00Z`, точность до секунды. Идентификаторы пользователей и контента — целые числа. **`content_id = 0` является допустимым значением.**

**Каталог:** `content_id`, `category`, `duration_seconds`. Одна строка на объект, длительность в секундах.

**События:**

| Поле | Значение |
|---|---|
| `event_id` | Идентификатор бизнес-события; повторная доставка сохраняет этот ID. |
| `event_time` | Время совершения действия. Для просмотра — момент его завершения. |
| `user_id` | Пользователь. |
| `event_type` | `view` или `search`. |
| `content_id`, `watch_time_seconds` | Для `view` — контент и просмотренные секунды; для `search` — `null`. |
| `query` | Для `search` — текст поиска; для `view` — `null`. |
| `available_at` | Модельное время поступления сообщения, определяющее порядок воспроизведения. |

**Изменения профилей:** `change_id`, `user_id`, `effective_at`, `country`, `subscription_tier`, `available_at`. Сообщение содержит полное состояние страны и тарифа с момента `effective_at`, а не частичное обновление. Начальное состояние также передаётся сообщением. Интервалы действия трактуются как `[начало, конец)`: событие на границе относится к новой версии. Одинаковое состояние может прийти с новым `change_id`; повторная доставка сохраняет старый `change_id`. Повтор состояния не создаёт новую SCD2-версию. В наборах нет разных состояний одного пользователя с одинаковым `effective_at`.

`event_id` и `change_id` — строки. Страна задаётся кодом `RU`, `KZ`, `BY` или `AM`, тариф — `basic`, `standard` или `premium`. Для исторического JOIN нужна история профиля, включающая состояние до начала расчётного периода.

`available_at` не является временем события, временем действия профиля или фактическим временем загрузки в хранилище. У повторных доставок оно может различаться, остальные поля сообщения с тем же ID совпадают. Файлы упорядочены по `available_at`, но не по `event_time` / `effective_at`. Наборы запускаются раздельно: их не нужно смешивать в одних расчётах.

Для одинаковой трактовки показателей:

- Один уникальный `view` — один просмотр; всё его время относится к минуте `event_time`. Поиск в показатели просмотров не входит.
- Общая витрина имеет детализацию «минута + content_id» и содержит количество просмотров и сумму `watch_time_seconds`. Историческая витрина — «дата UTC + страна + тариф» с теми же показателями. Страна и тариф определяются на момент каждого просмотра.
- Дневной топ-5 строится по количеству просмотров, при равенстве — по возрастанию `content_id`; сутки определяются в UTC.
- Частоты слов считаются по дням UTC, по уникальным поисковым событиям: нижний регистр, разделение по пробельным символам, только слова длиннее четырёх символов. Повтор слова внутри одного запроса учитывается.

## Какие ситуации заложены

В обоих наборах есть повторная доставка, новое сообщение с неизменным состоянием профиля, смена страны и тарифа, возврат к прежнему состоянию, просмотры на границах версий и суток. Позднее изменение профиля поступает после более новых версий; отдельный просмотр и повтор старого просмотра поступают после завершения основного периода. В demo также есть популярный контент, создающий перекос распределения.

Для готовых наборов основную часть можно отправить до `2026-01-04T00:00:00Z` по `available_at`, выполнить пакетный расчёт за прошедшие дни, затем отправить оставшиеся сообщения и пересчитать историю. Это граница этапов доставки, **не автоматически выбранная граница T общего отчёта**.

Чтобы увидеть в одном отчёте оба слоя, после первой отправки можно опубликовать пакетный расчёт только за 1 января и установить T на начало 2 января. Тогда 1 января берётся из пакетного слоя, а 2–3 января — из оперативного. Расчёты готовых наборов запускаются на исторические даты января 2026 года, независимо от текущей даты компьютера.

## Использование

Все команды ниже выполняются из каталога `final_project`. Генерация и `--dry-run` требуют только Python 3.9+; для отправки в Kafka нужна дополнительная зависимость. Инфраструктуру и два топика студенты подготавливают сами.

Проверить чтение готового набора без Kafka:

```bash
python3 scripts/replay_kafka.py --dataset data/fixture --dry-run
```

Установить зависимость в своё Python-окружение и отправить набор в Kafka:

```bash
python3 -m pip install -r scripts/requirements.txt
python3 scripts/replay_kafka.py --dataset data/demo --bootstrap-servers localhost:9092 --rate 100
```

По умолчанию используются топики `cinema.events` и `cinema.profile_changes`; их можно изменить через `--events-topic` и `--profiles-topic`. Ключ Kafka — `user_id`, значение — исходная JSON-строка. Каталог загружается в хранилище отдельно. Скрипт не создаёт топики, таблицы или инфраструктуру.

Вместо полной отправки можно выполнить два этапа:

```bash
python3 scripts/replay_kafka.py --dataset data/fixture --until-arrival 2026-01-04T00:00:00Z
# После обработки первой части и пакетного расчёта:
python3 scripts/replay_kafka.py --dataset data/fixture --from-arrival 2026-01-04T00:00:00Z
```

Нижняя граница включается, верхняя исключается. Скорость задаётся в сообщениях в секунду (`--rate 0` — без ограничения); дни модельного времени проигрываются ускоренно. Порядок отправки учитывает `available_at`, но Kafka не гарантирует общий порядок обработки между разными топиками и партициями. Перед пакетным расчётом нужно дождаться сохранения нужных сообщений в архив.

Повторный запуск скрипта повторно отправляет выбранные сообщения с прежними ID. Скрипт не ведёт позицию продолжения; после сбоя выбранный диапазон можно переотправить. Повторы должны обрабатываться студенческим решением. Фактические метаполя загрузки студенты записывают сами. Для защищённого брокера есть `--client-config` — путь к собственному JSON с настройками Kafka-клиента; секреты не следует помещать в репозиторий.

## Генерация нового набора

```bash
python3 scripts/generate_data.py --mode demo --events 100000 --users 1000 --days 7 --seed 42 --output data/custom
python3 scripts/generate_data.py --mode fixture --output data/custom_fixture
```

`--events` задаёт число уникальных событий: повторные доставки добавляются сверху. Параметры `--events`, `--users`, `--days`, `--seed` относятся к demo; fixture имеет фиксированный сценарий. Дату начала можно изменить через `--start-time` — полночь UTC. Повтор с теми же параметрами и каталогом создаёт идентичные файлы. Результат пишется только в новый или пустой каталог.

Генератор сохраняет сообщения в памяти для сортировки по времени доставки: при увеличении объёма учитывайте доступную RAM. Отправка в Kafka читает файлы последовательно. Параметры готового demo: 6 000 событий, 100 пользователей, 3 дня, seed 42, начало `2026-01-01T00:00:00Z`. Для нового набора граница двух этапов записана в `manifest.json` как `suggested_arrival_cutoff`.
