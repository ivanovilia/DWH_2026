# Минимальные требования к проекту

Проект должен обрабатывать данные от поступления в Kafka до итоговых витрин в ClickHouse. Инфраструктура разворачивается самостоятельно согласно [требованиям](INFRASTRUCTURE.md).

Студенты самостоятельно проектируют схемы таблиц, типы данных, ключи, партиционирование и движки ClickHouse; организацию хранения в S3; состав задач, зависимости и расписание DAG; способы дедупликации, построения SCD2 и повторного расчёта. При этом необходимо соблюдать заданную архитектуру, [контракт входных данных и определения показателей](data/README.md). Основные проектные решения нужно кратко обосновать в README своей работы.

## Что должно быть реализовано

1. **Оперативная загрузка:** Kafka → ClickHouse Kafka Engine → materialized view → целевые таблицы. Доступны количество просмотров и суммарное время просмотра по минуте и объекту контента.
2. **Полный архив в S3:** события, изменения профилей и каталог контента. Архивирование из Kafka использует отдельную consumer group и сохраняет в том числе опоздавшие сообщения.
3. **SCD2 профилей:** история страны и тарифа пользователя с интервалами действия версий. Интервалы одного пользователя не пересекаются.
4. **Пакетные расчёты на Spark:** очистка и дедупликация, JOIN просмотров с каталогом и исторический JOIN с профилем на момент события. В ClickHouse публикуются общие поминутные показатели, дневная витрина по стране и тарифу, дневной топ-5 контента и частоты поисковых слов.
5. **Сверка RDD и DataFrame:** на одном контрольном наборе из S3 посчитаны частоты поисковых слов и дневной топ-5 контента; результаты двух реализаций на Spark сверены по одинаковым правилам.
6. **Airflow DAG по расписанию:** подготовка данных, SCD2, JOIN, расчёт витрин, проверки и публикация в ClickHouse связаны зависимостями. Расчётный период определяется параметрами запуска; можно пересчитать исторический период.
7. **Общий отчёт в ClickHouse:** опубликованные пакетные показатели до границы T и оперативные показатели от T включительно объединяются без пропусков и двойного учёта периодов. Метрики и детализация совпадают; T проходит по границе минуты и обновляется только после успешной публикации всех закрываемых интервалов.

## Базовая корректность

- Повторы событий не завышают итоговые показатели. Повторный запуск расчёта на том же входном срезе не создаёт дублей и не меняет бизнес-показатели.
- Поздние события и изменения профилей учитываются при пересчёте затронутой истории. Для исторического JOIN используется версия профиля на дату события, а не текущая версия.
- В таблицах, формируемых по расписанию, есть метаполя: идентификатор запуска, расчётный интервал и время обработки. По результату можно определить, каким запуском он получен.
- Перед публикацией проверяются уникальность ключей витрин, отсутствие пересечений SCD2 и соответствие каждого просмотра ровно одной версии профиля и одному объекту каталога. Неуспешные проверки останавливают публикацию.

## Что приложить

Код, DDL, DAG, собственные конфигурации развёртывания и короткий README с порядком запуска и примерами запросов к итоговым отчётам. Для демонстрации должны быть примеры обычной обработки, повторного запуска и пересчёта после поступления поздних данных.
